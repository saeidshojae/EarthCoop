# FCM system notification open implementation plan

> **For agentic workers:** Use superpowers:executing-plans inline with RED/GREEN evidence.

**Goal:** Wire foreground and system-notification open events to authoritative account-scoped recovery and typed navigation.

**Architecture:** An SDK adapter supplies cold, warm and foreground events to a lifecycle-owned binding. Cold events are processed before buffered warm events, with bounded duplicate tracking. Each open resolves the notification ID through the authenticated read endpoint and uses the returned typed link, guarded by the captured session before/after await. Runtime navigation checks the live session and freshly verified bootstrap.

**Tech Stack:** Existing Flutter/Firebase Messaging, GoRouter, Dart tests.

**Spec:** docs/FIREBASE_FCM_OPEN_DESIGN.md

## Global constraints

- No package, broad permission, host publication, raw URL navigation or secret logging.
- Start SDK intake after Firebase initialization; dispose subscriptions with the runtime.
- Never trust push payload link as authorization; read endpoint validates notification owner.
- Leave real phone receipt/tap UAT open. Only latest final candidate requires phone testing.

## Review focus

- Cold/warm duplicates must navigate once; foreground receipt must not consume a later tap.
- Changed session or disposed runtime during network recovery must not navigate.
- Malformed/missing notification ID must not call the read endpoint.
- Forged payload link must not override the authoritative response.
- Bootstrap failure, forbidden read or unsupported typed route must not navigate.
