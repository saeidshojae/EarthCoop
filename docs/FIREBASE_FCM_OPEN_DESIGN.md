# FCM open design

Use FirebaseMessaging.getInitialMessage, onMessageOpenedApp and onMessage only after Firebase initialization. Adapter converts them to immutable FcmMessageEvent(messageId, data). FcmMessageBinding owns subscriptions, buffers warm events until cold intake is known, serializes callbacks and retains at most 128 successful event IDs separately for opens and foreground receipts. SDK startup is idempotent, failure-isolated and teardown rejects queued/late events.

AuthorizedPushOpen reads context.notification_id (JSON string or object) with a bounded safe identifier grammar. It snapshots active session scope, calls the existing authenticated /notifications/{id}/read with an idempotency key, checks the scope after awaiting and opens only the server response link. Never open payload fallback_url/raw link. Foreground receipts trigger account-scoped notification recovery without navigation or read mutation. Runtime open checks live authentication, fresh compatible/protected bootstrap and the typed route registry; disposed runtime returns false. Unknown/forbidden/offline events safely leave the app usable. Cold event while signed out is obtained only once SDK initializes for an authenticated session; the server verifies whether that account owns it.

No host driver activation, no native foreground banner and no Huawei event receiver is added in this bounded FCM checkpoint. Android system background rendering is handled by the existing Firebase notification payload/SDK. Real delivery, cold/warm tap and permission prompts remain phone UAT, while deterministic tests cover callback and account boundaries.

Receipt-time scope is captured for warm/foreground events and before cold initial-message lookup, and checked again at serialized dispatch. The mounted inbox subscribes to a runtime-owned foreground refresh stream; without a mounted inbox, recovery uses a disposable account-scoped controller. Queue/buffer and successful-event history each have a combined bound of 128; event keys distinguish open vs foreground. Known minor follow-ups: separate history capacities and foreground recovery retry signaling; see the progress receipt.
