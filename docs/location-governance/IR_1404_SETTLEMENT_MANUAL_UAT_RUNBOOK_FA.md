# UAT دستی جریان آبادی‌های مرجع ایران ۱۴۰۴

**وضعیت:** فقط برای UAT / staging یا محیط محلی ایزوله. این سند مجوز merge، اجرای migration روی Production، فعال‌سازی feature flag در سایت زنده یا cutover v1→v2 نیست.

## کاندید مورد آزمون

پیش از شروع، SHA دقیق شاخه را ثبت کنید و فقط همان نسخه را تست کنید. Full Validation، Responsive Validation و Iran staging باید برای همان SHA سبز باشند.

Feature flagهای لازم فقط در محیط UAT:

- `IR_SETTLEMENT_CATALOG_ENABLED=true`
- `IR_SETTLEMENT_CLAIMS_ENABLED=true`

در Production این دو flag باید خاموش بمانند تا مجوز release جداگانه صادر شود.

## دادهٔ آزمون پیشنهادی

برای UAT دستیِ اولیه، از مسیرهایی استفاده کنید که parent crosswalk آن‌ها در قرارداد فعلی `verified_identity` است. مثال مناسب برای مسیر روستایی ساری:

ایران → مازندران → شهرستان ساری → بخش چهاردانگه → دهستان چهاردانگه

شناسهٔ v2 دهستان در crosswalk فعلی:

`IR-1404-1938`

برای تست fail-closed از settlementای استفاده کنید که parent آن crosswalk قطعی ندارد. این تست نباید با دستکاری مستقیم DB انجام شود؛ fixture/UAT data باید از قبل آماده باشد.

## سناریو A — جست‌وجوی آبادی در Step 3

1. با کاربر تست وارد Step 3 ثبت‌نام شوید.
2. مسیر canonical را تا والد معتبر انتخاب کنید.
3. بخش «آبادی مرجع» باید فقط وقتی parent قابل نگاشت قطعی است قابل استفاده باشد.
4. حداقل دو حرف از نام آبادی را جست‌وجو کنید.
5. نتیجه باید نام آبادی را نشان دهد و آن را «در انتظار بررسی» معرفی کند.

**قبولی:**
- آبادی از کاتالوگ مرجع پیدا می‌شود؛
- هیچ `Location` جدیدی صرف جست‌وجو ساخته نمی‌شود؛
- UI آن را روستای تأییدشده یا حوزهٔ حکمرانی رسمی معرفی نمی‌کند.

## سناریو B — تکمیل ثبت‌نام با آبادی مرجع

1. یکی از آبادی‌های نتیجهٔ سناریو A را انتخاب کنید.
2. ثبت‌نام را تکمیل کنید.
3. وارد Dashboard شوید.

**قبولی:**
- ثبت‌نام کامل می‌شود؛
- محل دقیق آبادی در وضعیت pending باقی می‌ماند؛
- Primary Residence موقتاً روی parent canonical قطعی قرار می‌گیرد؛
- برای خود settlement هیچ `Location`، `GovernanceArea` یا گروه رسمی فعال ساخته نمی‌شود؛
- کاربر حق رأی مستقل برای settlement دریافت نمی‌کند.

## سناریو C — نمایش بعد از ثبت‌نام

### مکان و حکمرانی من

به «مکان و حکمرانی من» بروید.

باید:
- نام آبادی انتخابی دیده شود؛
- عبارت روشن «در انتظار بررسی» وجود داشته باشد؛
- توضیح داده شود که حوزهٔ رسمی فعلی هنوز همان parent canonical است.

### پروفایل

به ویرایش پروفایل / بخش مکان بروید.

باید همان settlement pending دیده شود و با residence/governance رسمی اشتباه نشود.

## سناریو D — گروه‌های pending

صفحهٔ گروه‌های کاربر را بررسی کنید.

**قبولی:**
- گروه‌های مربوط به settlement فقط به‌صورت pending shell باقی می‌مانند؛
- parent canonical نباید به‌خاطر settlement pending به base active تبدیل شود؛
- هیچ گروه رسمی فعالِ مخصوص settlement ساخته نشده باشد؛
- هیچ گروه pending قدیمی/شبح از انتخاب قبلی همزمان باقی نماند.

## سناریو E — ده حمایت مستقل

با کاربران UAT جداگانه همان settlement را انتخاب/claim کنید تا به threshold تنظیم‌شده برسد.

**قبولی:**
- هر کاربر فقط یک بار برای همان settlement شمرده می‌شود؛
- settlement در صف ادمین بالاتر می‌آید؛
- رسیدن به threshold هیچ‌کدام از موارد زیر را خودکار ایجاد نمی‌کند:
  - residential eligibility تأییدشده؛
  - اقامت رسمی کاربر؛
  - GovernanceArea؛
  - گروه رسمی فعال؛
  - حق رأی.

## سناریو F — مرکز کنترل ادمین: مدرک بیشتر لازم است

1. وارد مرکز کنترل Location/Governance شوید.
2. settlement را در صف بررسی پیدا کنید.
3. تصمیم «مدرک بیشتری لازم است» را با دلیل ثبت کنید.

**قبولی:**
- settlement وارد وضعیت `needs_review` می‌شود؛
- claimهای باز به `needs_evidence` می‌روند؛
- کاربران جدید همچنان می‌توانند همان settlement را claim کنند؛
- هیچ تأیید مسکونی یا حکمرانی ایجاد نمی‌شود.

## سناریو G — تأیید ماهیت مسکونی با مدرک

برای settlement تست، تصمیم «شواهد معتبر روستای مسکونی» را انتخاب کنید.

بدون هر سه مورد زیر ثبت تصمیم نهایی باید رد شود:
- مرجع/سازمان صادرکننده؛
- تاریخ مدرک؛
- شناسه یا نشانی مرجع مدرک.

با مدرک کامل:

**قبولی:**
- classification به `verified_residential_village` تغییر می‌کند؛
- residential eligibility تأیید می‌شود؛
- claim به `residential_evidence_verified` می‌رود؛
- اما `governance_authorized=false` باقی می‌ماند؛
- settlement هنوز به‌تنهایی اقامت رسمی/گروه رسمی/حق رأی ایجاد نمی‌کند.

## سناریو H — رد غیرمسکونی

روی یک settlement تست دیگر، با مدرک کامل تصمیم غیرمسکونی ثبت کنید.

**قبولی:**
- settlement `verified_nonresidential_place` می‌شود؛
- claimهای باز `rejected` می‌شوند؛
- PendingResidenceIntent مربوطه `cancelled` می‌شود؛
- pending group shellها `rejected` می‌شوند؛
- parent canonical residence کاربر خودکار جابه‌جا یا حذف نمی‌شود.

## سناریو I — fail-closed برای parent نامشخص

settlementای با parent بدون crosswalk قطعی انتخاب کنید.

**قبولی:**
- Step 3 اجازهٔ تکمیل از این مسیر نمی‌دهد؛
- پیام خطای قابل‌فهم نمایش داده می‌شود؛
- هیچ residence relationship، claim، pending intent یا group shell نیمه‌کاره ایجاد نمی‌شود.

## سناریو J — خاموش بودن feature flag

هر یک از flagهای settlement را در محیط UAT خاموش کنید.

**قبولی:**
- جست‌وجو/claim/ثبت‌نام settlement در دسترس نیست؛
- مسیرهای canonical قدیمی بدون مشکل کار می‌کنند؛
- هیچ خطای 500 یا UI نیمه‌فعال نباید دیده شود.

## سناریو K — موبایل و RTL

حداقل در viewport موبایل و دسکتاپ بررسی کنید:

- Step 3 و نتایج جست‌وجوی settlement؛
- My Location & Governance؛
- پروفایل؛
- صف ادمین.

**قبولی:**
- overflow افقی وجود ندارد؛
- دکمه‌ها و فرم evidence قابل لمس/خواندن‌اند؛
- متن pending و هشدارها بریده یا روی هم افتاده نیستند.

## شواهدی که برای هر سناریو ثبت شود

برای هر تست فقط این موارد کافی است:

- شناسه سناریو؛
- PASS / FAIL؛
- screenshot در صورت اشکال UI؛
- نام/شناسه settlement؛
- user تست؛
- توضیح کوتاه رفتار غیرمنتظره.

نیازی به SQL دستی برای «درست‌کردن» نتیجهٔ UAT نیست. اگر سناریویی FAIL شد، داده را دستی اصلاح نکنید؛ failure باید از مسیر کد/contract بررسی شود.

## چیزهایی که در این UAT نباید انجام شوند

- اجرای importer روی Production؛
- فعال‌کردن settlement feature flags روی سایت زنده؛
- اجرای v1→v2 cutover؛
- حذف v1؛
- تبدیل support ده‌کاربره به approval؛
- ساخت دستی GovernanceArea برای settlement؛
- اصلاح دستی claim/intent/group shell در DB برای سبزکردن UAT.

## مرحلهٔ بعد از UAT

اگر همه سناریوهای بالا سبز باشند:

1. runtime audit فقط‌خواندنی روی DB فعلی اجرا می‌شود؛
2. تمام v1 identityهای حاضر و وابستگی‌های کاربران/گروه‌ها/proposalها بررسی می‌شوند؛
3. Sari municipality reconciliation جداگانه بسته می‌شود؛
4. سپس و فقط سپس طرح shared-DB cutover و rollback برای بررسی آماده می‌شود.
